# GRSAI / RunningHub 异步图像 API 接口资料

核查日期：2026-10-15

先明确三个关键结论：

1. GRSAI 使用 `POST /v1/api/generate` 提交任务，`GET /v1/api/result?id=...` 查询任务，结果图片位于 `results[].url`。
2. RunningHub 存在两套接口：新版 Standard Model API 使用 `/openapi/v2/...` 提交及 `/openapi/v2/query` 查询；传统 AI App / Workflow API 则使用 `/task/openapi/...`。两套接口的响应结构不同，不能混用。
3. 提交超时不等于提交失败。HTTP 客户端超时后，服务端仍可能已创建任务。若没有收到任务 ID，直接重试可能造成重复生成和重复计费。两家的客户端都必须处理这种不确定状态。

以下以官方文档为依据，Key 全部脱敏。真实文档示例与为说明异常处理而构造的示例会明确区分。

## 一、GRSAI

来源：[生成接口](https://qmy27nhsd9.apifox.cn/452409160e0)、[异步查询接口](https://qmy27nhsd9.apifox.cn/452409577e0)

### 1. Submit：任务提交

| 项目      | 接口规范                                         |
| ------- | -------------------------------------------- |
| HTTP 方法 | `POST`                                       |
| 全球 URL  | `https://grsaiapi.com/v1/api/generate`       |
| 国内 URL  | `https://grsai.dakka.com.cn/v1/api/generate` |
| 鉴权头     | `Authorization: Bearer <API_KEY>`            |
| 内容类型    | `Content-Type: application/json`             |
| 任务 ID   | `id`                                         |
| 任务状态    | `status`                                     |

请求体（根据官方示例改为 `gpt-image-2.5`）：

```
{
  "model": "gpt-image-2.5",
  "prompt": "A studio portrait of a woman",
  "images": [],
  "aspectRatio": "1024x1024",
  "quality": "auto",
  "replyType": "json"
}
```

成功响应：HTTP 200

```
{
  "id": "14-5f3cf761-a4bb-486a-8016-77f490998f80",
  "status": "succeeded",
  "results": [
    {
      "url": "https://file1.aitohumanize.com/file/example.png"
    }
  ]
}
```

官方还列出了 HTTP 200 异步返回、HTTP 400 错误两种响应类别，但当前可读取的公开页面没有展开这两种响应的完整 JSON，因此不能将其中的字段或错误码视为已验证。

### 2. Poll：异步查询

| 项目      | 接口规范                                                    |
| ------- | ------------------------------------------------------- |
| HTTP 方法 | `GET`                                                   |
| 全球 URL  | `https://grsaiapi.com/v1/api/result?id=<TASK_ID>`       |
| 国内 URL  | `https://grsai.dakka.com.cn/v1/api/result?id=<TASK_ID>` |
| 鉴权头     | `Authorization: Bearer <API_KEY>`                       |
| 请求体     | 无                                                       |
| 查询参数    | `id`                                                    |
| 状态字段    | `status`                                                |
| 图片数组    | `results`                                               |
| 图片 URL  | `results[].url`                                         |

请求示例：

```
curl -X GET \
  'https://grsaiapi.com/v1/api/result?id=14-5f3cf761-a4bb-486a-8016-77f490998f80' \
  -H 'Authorization: Bearer <API_KEY>'
```

官方查询成功响应与提交成功响应结构一致：

```
{
  "id": "14-5f3cf761-a4bb-486a-8016-77f490998f80",
  "status": "succeeded",
  "results": [
    {
      "url": "https://file1.aitohumanize.com/file/example.png"
    }
  ]
}
```

多图片应按 `results[]` 数组处理，而不是假定永远只有一张。公开示例展示的是单张图片，未明确保证数组排序规则。

### 3. 异步状态与失败示例

如果需要真正的异步工作流，`replyType` 应改为 `async`，而不是 `json`。

```
{
  "model": "gpt-image-2.5",
  "prompt": "A studio portrait",
  "images": [],
  "aspectRatio": "1024x1024",
  "replyType": "async"
}
```

异步提交成功示例：

```
{
  "id": "task-001",
  "status": "running"
}
```

官方 ComfyUI-GrsAI 客户端源码采用以下状态集合：

| 状态类别  | 状态值                                                       |
| ----- | --------------------------------------------------------- |
| 成功    | `succeeded`                                               |
| 等待中   | `running`, `pending`, `queued`, `processing`, `submitted` |
| 失败或终止 | `failed`, `violation`, `cancelled`, `canceled`            |

这是客户端代码的兼容处理范围，不代表所有状态都会由服务端实际返回。

### 4. 结果有效期与重新查询

- 结果 URL 有效期： 这两份 Apifox 文档没有给出统一有效时间。不过，GRSAI 于 2026-09-15 的 MiniMax H3 公告中说明生成图片和视频保留 2 小时。该说明是否覆盖全部 GPT Image 模型，尚不能确认。
- 按任务 ID 重查： 支持，通过 `GET /v1/api/result?id=...`。
- URL 失效后重新查询： 没有找到重新签发有效 URL 或恢复已删除文件的保证；因此不能依赖这种恢复方式。
- 下载鉴权： 官方提供独立的结果文件链接，现有示例没有要求再次携带 API Key，但尚无正式的匿名下载保证或响应头规范。
- 多图结果： `results[]`，每个元素有 `url`，需要逐张下载、逐张记录错误。

## 二、RunningHub（Standard Model API / V2）

你提供的 RunningHub 详情页本次无法完整读取。因此，下面使用能够核实的官方 gpt-image-2/image-to-image-official-stable 作为具体请求实例；它的 Endpoint 已由独立 API 文档确认。不能断言这个 Endpoint 与你提供的页面 ID 完全相同。

来源：[模型 API 文档](https://www.runninghub.cn/runninghub-api-doc-en/api-448969336)、[V2 查询文档](https://www.runninghub.cn/runninghub-api-doc-en/api-425767807)、[错误码文档](https://www.runninghub.cn/runninghub-api-doc-cn/doc-8435517)

### 1. Submit：任务提交

| 项目      | 接口规范                                                                           |
| ------- | ------------------------------------------------------------------------------ |
| HTTP 方法 | `POST`                                                                         |
| 完整 URL  | `https://www.runninghub.ai/openapi/v2/rhart-image-g-2-official/image-to-image` |
| 鉴权头     | `Authorization: Bearer <API_KEY>`                                              |
| 内容类型    | `Content-Type: application/json`                                               |
| 任务 ID   | `taskId`                                                                       |
| 任务状态    | `status`                                                                       |
| 错误信息    | `errorCode`, `errorMessage`                                                    |

请求体：

```
{
  "prompt": "Refine the image details",
  "imageUrls": [
    "https://example.com/input.png"
  ],
  "aspectRatio": "3:4",
  "resolution": "2k",
  "quality": "medium"
}
```

成功受理响应（官方结构）：

```
{
  "taskId": "2013508786110730241",
  "status": "RUNNING",
  "errorCode": "",
  "errorMessage": "",
  "results": null,
  "clientId": "f828b9af25161bc066ef152db7b29ccc",
  "promptTips": "{\"result\":true,\"error\":null,\"outputs_to_execute\":[\"4\"],\"node_errors\":{}}"
}
```

### 2. Poll：任务查询

| 项目      | 接口规范                                         |
| ------- | -------------------------------------------- |
| HTTP 方法 | `POST`                                       |
| 完整 URL  | `https://www.runninghub.ai/openapi/v2/query` |
| 鉴权头     | `Authorization: Bearer <API_KEY>`            |
| 内容类型    | `Content-Type: application/json`             |
| 请求体     | `{"taskId":"2013508786110730241"}`           |
| 状态字段    | `status`                                     |
| 图片 URL  | `results[].url`                              |

官方状态：`QUEUED`、`RUNNING`、`SUCCESS`、`FAILED`。

成功响应（URL 脱敏）：

```
{
  "taskId": "2013508786110730241",
  "status": "SUCCESS",
  "errorCode": "",
  "errorMessage": "",
  "failedReason": {},

    }
  ],
  "clientId": "",

```


### 3. 多图片与 URL 有效期

多图片结果是 `results[]` 数组，每张图片分别包含 `url`、`outputType`，可能还包含 `nodeId`、`text` 等字段。

```
{
  "status": "SUCCESS",
  "results": [
    {"url": "https://example.com/a.png", "outputType": "png"},
    {"url": "https://example.com/b.png", "outputType": "png"}
  ]
}
```

这是展示多图结构的模拟精简样例。

有效期：24 小时。 RunningHub 模型详情页明确说明结果链接只有 24 小时有效，失效后无法恢复。虽然文案部分使用了 video 一词，但这一规则也显示在图像模型的结果字段说明中。建议所有输出都立即下载并持久化保存。

### 4. Upload：图片上传（新版）

| 项目      | 接口规范                                                   |
| ------- | ------------------------------------------------------ |
| HTTP 方法 | `POST`                                                 |
| 完整 URL  | `https://runninghub.cn/openapi/v2/media/upload/binary` |
| 鉴权头     | `Authorization: Bearer <API_KEY>`                      |
| 内容类型    | `multipart/form-data`                                  |
| 表单字段    | `file`                                                 |
| 返回状态    | `code`, `message`                                      |
| 可访问链接   | `data.download_url`                                    |
| 文件路径    | `data.fileName`                                        |
| 文件大小    | `data.size`                                            |

请求：

```
curl -X POST \
  'https://runninghub.cn/openapi/v2/media/upload/binary' \
  -H 'Authorization: Bearer <API_KEY>' \
  -F 'file=@/path/to/input.png'
```

成功响应（官方结构，内容脱敏）：

```
{
  "code": 0,
  "message": "success",
  "data": {
    "type": "image",
    "download_url": "https://example.com/input.png",
    "fileName": "openapi/xxxx.png",
    "size": "3490"
  }
}
```

其中 `download_url` 是可供输入使用的访问链接，`fileName` 是服务端文件路径，`size` 是服务端返回的文件大小字段。

上传链接有效期同样为 1 天。 到期后不能继续通过原 URL 直接访问；原始上传文件在服务端保留多久、内部 `fileName` 是否继续可用，则没有在该页面得到相同保证。

## 三、RunningHub 传统 AI App / Workflow API 的区别

如果你的现有代码使用的是传统 `/task/openapi/...` 接口，需要使用另一套字段。

| 阶段              | HTTP URL                                                 | 关键字段                                   |
| --------------- | -------------------------------------------------------- | -------------------------------------- |
| Submit Workflow | `POST https://www.runninghub.ai/task/openapi/create`     | `apiKey`, `workflowId`, `nodeInfoList` |
| Submit AI App   | `POST https://www.runninghub.ai/task/openapi/ai-app/run` | `apiKey`, `webappId`, `nodeInfoList`   |
| Poll            | `POST https://www.runninghub.ai/task/openapi/outputs`    | `apiKey`, `taskId`                     |
| Upload          | `POST https://www.runninghub.ai/task/openapi/upload`     | Multipart：`apiKey`, `file`, `fileType` |

例如 Workflow Submit：

```
{
  "apiKey": "<API_KEY>",
  "workflowId": "1904136902449209346",
  "nodeInfoList": [
    {
      "nodeId": "6",
      "fieldName": "text",
      "fieldValue": "A studio portrait"
    }
  ]
}
```

提交成功的任务 ID 位于 `data.taskId`。

传统 Poll 成功响应：

```
{
  "code": 0,
  "msg": "success",
  "data": [
    {
      "fileUrl": "https://example.com/output.png",
      "fileType": "png",
      "taskCostTime": "83",
      "nodeId": "12"
    }
  ]
}
```

传统 Poll 的业务状态码：`804` 运行中、`813` 排队中、`805` 失败、`0` 且有输出数据表示成功。这里的 `code` 不是 HTTP 状态码。

## 四、Download：结果下载及元数据

GRSAI 和 RunningHub 都是从结果 JSON 中取出图片 URL，之后独立发起下载。

```
GET <RESULT_IMAGE_URL>
```

现有官方文档未强制要求在图片下载请求中添加生成 API Key，但也没有统一规定所有 CDN 的匿名访问权限与 HTTP 响应头。

正常图片下载可能出现的响应头（示意，非实测）：

```
HTTP/1.1 200 OK
Content-Type: image/png
Content-Length: <BYTES>
ETag: <ETAG>
Last-Modified: <HTTP_DATE>
Cache-Control: <CACHE_POLICY>
```

其中只有图片类型与字节内容可以通过实际下载核对，`ETag`、`Last-Modified`、`Content-Disposition` 等字段不保证存在。

| 信息                 | 获取方式                            |
| ------------------ | ------------------------------- |
| 图片 MIME            | HTTP `Content-Type`             |
| 图片文件大小             | `Content-Length` 或实际字节数         |
| 图片宽高               | 解码 PNG/JPEG/WebP                |
| EXIF / ICC Profile | 读取图片元数据                         |
| 文件是否完整             | 图片解码 + 文件长度检查                   |
| CDN 过期时间           | 官方规则或 URL 签名信息；并非所有链接都有可解析的过期参数 |

可使用下面的命令检查真实返回内容：

```
curl -L -D headers.txt \
  --connect-timeout 10 \
  --max-time 120 \
  '<RESULT_IMAGE_URL>' \
  -o result.png

file result.png
sips -g pixelWidth -g pixelHeight result.png
```

需要注意：HTTP 200 不等于下载成功。还要检查 Content-Type 是否为图片、实际文件是否完整，以及能否解码。CDN 也可能返回 HTML 或 JSON 错误页面。

## 五、失败、超时与异常响应样例

以下表格中的异常样例为客户端测试用例，不是声称真实抓取到的服务端报文。超时示例采用常见 Python `requests` 异常表示法。

| 服务商 / 阶段             | 成功判定                      | 失败示例                     | 超时或响应异常                        |
| -------------------- | ------------------------- | ------------------------ | ------------------------------ |
| GRSAI Submit         | `200`，返回 `id`             | HTTP `400` 参数错误          | `ReadTimeout`，可能已创建任务          |
| GRSAI Poll           | `status=succeeded`        | `status=failed`          | `ReadTimeout` / 非法 JSON        |
| GRSAI Download       | HTTP `200` + 有效图片         | HTTP `403` / `404`（可能情况） | 下载中断 / 图片数据不完整                 |
| RunningHub V2 Submit | 有 `taskId`，状态受理           | `errorCode=1007` 参数错误    | `ReadTimeout` / `502`          |
| RunningHub V2 Poll   | `status=SUCCESS`          | `status=FAILED`，如 `1501` | `ReadTimeout` / `results` 结构异常 |
| RunningHub V2 Upload | `code=0`，有 `download_url` | 上传失败，如 `1517`            | `ReadTimeout` / 响应没有 `data`    |
| RunningHub Download  | HTTP `200` + 有效图片         | HTTP `403` / `404`（可能情况） | 下载中断 / 内容类型错误                  |

这里的 403、404、502 等是建议覆盖的故障测试场景，并不意味着平台保证过期时一定返回这些状态码。

推荐客户端超时配置（工程建议，不是服务端官方限制）：

| 阶段         | 连接超时 | 读取超时   | 超时处理         |
| ---------- | ---- | ------ | ------------ |
| Submit（异步） | 10s  | 30–60s | 无 ID 时标记为待确认 |
| Poll       | 10s  | 15–30s | 同一 ID 继续查询   |
| Upload     | 10s  | 120s   | 必要时重新上传      |
| Download   | 10s  | 120s   | 优先重试下载，不重新生成 |

Poll 的单次 HTTP 超时，与整个生成任务的最长等待时间，是两个独立配置。

### Submit 超时后，任务是否可能已创建？

两家都存在这种可能性。 原因是客户端等待响应超时，不代表服务端没有收到或执行请求。

推荐实现：

1. 提交前生成本地唯一 `job_id`，并持久化请求信息。
2. 收到远程 `taskId` / `id` 后立即保存。
3. Submit 超时且没有 ID 时，将状态设为 `SUBMISSION_UNKNOWN`，不能直接视为失败。
4. 在没有服务端幂等键或可按本地请求 ID 查询的接口保证前，不自动无限重试 Submit。
5. Poll 超时则安全得多：保留远程任务 ID，继续查询原任务即可。
